控制指令怎麼到馬達？ DDS / topic / SHM

ros2_control + ethercat_driver_ros2 · 實測背景：gx701 phu_controller_ros2 = JTC @ 500 Hz、ec_master.cpp 設 SCHED_FIFO

一句話：JTC 架構下，控制指令根本不經 DDS — controller 與 EtherCAT 硬體在同一 process、同一 RT 執行緒，靠共享記憶體（double 參考）交換。DDS 只在「外部送整條軌跡進來」那一刻用一次。500 Hz 沒問題。

兩段通訊，RT 那段不走 DDS

共享記憶體（同 process，無 middleware） DDS（跨 process，僅軌跡一次性）

DDS 出現在哪 → JTC 與 FPC 天差地別

安全 JTC（你在用的）

軌跡目標用 FollowJointTrajectory action / ~/joint_trajectory topic 一次性送進來（走 DDS），之後 JTC 在 500 Hz 迴圈內自己內插。→ 每週期設定點不走 DDS。

當心 FPC（forward_position_controller）

訂閱 ~/commands（Float64MultiArray）topic，你發的每個設定點都過 DDS。若從外部逐拍串流 500 Hz~1 kHz → 每拍吃 DDS 延遲/抖動/掉包（掉包時沿用舊值）。

500 Hz 會有問題嗎

JTC @ 500 Hz（現況）：不會。 RT 迴圈是 in-process 共享記憶體 + SCHED_FIFO，DDS 只送一次軌跡。500 Hz 甚至 1 kHz 在 PREEMPT_RT 上都很輕鬆（EYOU EtherCAT 最小週期到 500 µs = 2 kHz 都在規格內）。
唯一要小心：FPC + 外部逐拍串流。 那段走 DDS，500 Hz~1 kHz 會踩抖動/掉包。對策：RT 友善 QoS（best-effort、keep-last-1）並接受抖動；或把設定點產生器做成 chained controller 塞進 RT 迴圈（就不過 DDS）。

補充

  • 瓶頸不在 middleware，在 update_rate 迴圈本身：只要有 RT 優先權、mlockall、隔離核（gx701 已套 isolcpus），500 Hz/1 kHz 的 read→update→write 綽綽有餘。天花板是 EtherCAT 週期與 CPU 算力，不是 DDS。
  • 與本 repo 同源思想：本 repo loop-engine 的 cmd ring（lock-free SPSC） 等同 ros2_control 的 in-process command interface——RT 端讀、非 RT 端寫，兩者都讓 RT 迴圈不碰 middleware；差別只在本 repo 沒有 DDS 外圍層。
