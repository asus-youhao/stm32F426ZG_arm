7

CAN 匯流排基礎 · bxCAN 驅動

🎯 懂 CAN 訊框與仲裁，會算位元時序，能寫出中斷收包的驅動層。
  • 差動雙絞線 CAN_H/CAN_L，兩端 120Ω 終端電阻；多主廣播，ID 越小優先權越高（逐位仲裁）
  • Classic CAN 資料最多 8 bytes、1 Mbps 上限 — 這個「8 bytes」到 L2-11 會變成整個架構的天花板
  • 位元時序：1 bit = SYNC + BS1 + BS2 個 time quantum（TQ），取樣點通常擺 ~87.5%
1 Mbps 位元時序（APB1=45MHz 例，co_bxcan.c 實際設定）
/* 45 MHz / Prescaler 5 = 9 MHz → 1 bit = 9 TQ = 1 µs (1 Mbps)
 * 9 TQ = SYNC(1) + BS1(6) + BS2(2)，取樣點 = 7/9 ≈ 78% */
hcan.Init.Prescaler     = 5;
hcan.Init.TimeSeg1      = CAN_BS1_6TQ;
hcan.Init.TimeSeg2      = CAN_BS2_2TQ;
hcan.Init.SyncJumpWidth = CAN_SJW_1TQ;   /* 換時脈樹要重算！ */
RX 走中斷 + 環形佇列（firmware/canopen/co_bxcan.h 的分層）
/* ISR 只做「收進佇列」，解析留給主流程 — L1-5 的 ISR 準則 */
void HAL_CAN_RxFifo0MsgPendingCallback(CAN_HandleTypeDef *h)
{
    co_frame_t f = read_from_fifo(h);
    co_bxcan_on_rx(bus_of(h), &f);      /* 入環形佇列 */
}
/* 主流程/控制迴圈中: */
co_frame_t f;
while (co_bxcan_recv(CO_BUS_LEFT, &f)) {
    co_pdo_process_frame(CO_BUS_LEFT, &f);   /* L2-10 */
    co_nmt_process_frame(CO_BUS_LEFT, &f);   /* L2-8  */
}
💻 對照範例：learn/examples/l2/01-can-raw/（vcan 上收發第一個 frame）；repo 實例 firmware/canopen/co_bxcan.h/.c（CAN1=左臂、CAN2=右臂 @1Mbps）。實體接線與拓樸見 docs/design/can-bus-architecture.md。

CANopen 入門 · NMT / Heartbeat

🎯 懂 CANopen 的三大件（OD / COB-ID / NMT），能把節點帶進 Operational 並監看心跳。
概念是什麼本專案的例子
物件字典 OD每個節點一本「參數電話簿」，用 index:sub 定址0x6060 運行模式、0x607A 目標位置
COB-ID功能碼 + 節點 ID 組成的 CAN IDRPDO1=0x200+node、TPDO1=0x180+node、HB=0x700+node
NMT 狀態機Init → Pre-operational → Operational（PDO 只在 OP 跑）co_nmt_send(bus, NMT_START, 0) 廣播啟動
開機流程 + 心跳監看（co_nmt.h API）
/* 1) 廣播讓整條 bus 的 7 個關節進 Operational */
co_nmt_send(CO_BUS_LEFT, CO_NMT_CMD_START, 0 /* =all */);

/* 2) 週期檢查心跳年齡 — 超過 100ms 沒心跳就當失聯 */
for (uint8_t node = 1; node <= 7; node++) {
    if (co_nmt_node_age_ms(CO_BUS_LEFT, node) > 100)
        printf("node %u heartbeat lost!\r\n", node);
}
心跳是安全的地基：L3-16 的通訊看門狗、專案 A 的 50ms 逾時安全停止，底層都是這個 node_age_ms 概念。
💻 對照範例：learn/examples/l2/02-nmt-heartbeat/（對打 common/fake_slave.py 假關節）；repo 實例 firmware/canopen/co_nmt.h/.c、共用型別 canopen.h。

SDO — 讀寫物件字典（組態通道）

🎯 會用 SDO 在初始化階段組態關節：讀型號、設模式、設限位。

SDO 是「一問一答」的可靠通道（client→server 0x600+node，回應 0x580+node）。慢但可靠，所以只在初始化用；即時控制走 PDO：

用 SDO 組態一顆 PHU 關節（co_sdo.h API，expedited ≤4 bytes）
uint32_t device_type;
co_sdo_read (CO_BUS_LEFT, 1, 0x1000, 0, &device_type, 50);   /* 讀 Device Type */

co_sdo_write(CO_BUS_LEFT, 1, 0x6060, 0, 8 /*CSP*/, 1, 50);   /* 運行模式=CSP */
co_sdo_write(CO_BUS_LEFT, 1, 0x6081, 0, 100000, 4, 50);      /* Profile velocity */

uint32_t sw;
co_sdo_read (CO_BUS_LEFT, 1, 0x6041, 0, &sw, 50);            /* 讀 Statusword */
實戰教訓（本 repo 踩過）：對真實伺服關節，不要亂寫不認識的廠商自定義物件。本專案在 EtherCAT 路線上碰 0x2100（廠商物件）導致從站行為異常，最後靠對照原廠參考主站才定位（見專案 B 頁「實戰紀錄」）。先讀手冊、先 read-only 摸清楚，再寫。
💻 對照範例：learn/examples/l2/03-sdo-client/（讀/寫/abort 三情境都演）；repo 實例 firmware/canopen/co_sdo.h/.c（阻塞式 + 逾時，適合初始化）。

PDO — 即時資料交換（控制通道）

🎯 懂 PDO 映射，能每個控制週期下發目標、收回授。

PDO 是「事先講好格式、不用回應」的廣播 — 一個 frame 塞多個 OD 物件，這才是即時控制的主角。本專案映射（co_pdo.h）：

方向COB-ID內容（8 bytes 剛好用滿 6）
RPDO1 主站→關節0x200+nodeControlword(0x6040, u16) + Target Position(0x607A, i32)
TPDO1 關節→主站0x180+nodeStatusword(0x6041, u16) + Position Actual(0x6064, i32)
控制週期內的一來一回（co_pdo.h API）
/* 下發：控制字 + 目標位置（CSP 模式） */
co_pdo_send_csp(CO_BUS_LEFT, node, CW_ENABLE_OP, target_counts);

/* 收回授（由 co_pdo_process_frame 更新的快取） */
uint16_t sw; int32_t pos;
if (co_pdo_get_feedback(CO_BUS_LEFT, node, &sw, &pos)) {
    /* feedback_seq 有遞增才是「新」回授 — 安全看門狗靠這個判斷 */
}
SDO vs PDO 一句話：SDO 是打電話問一句答一句（組態）；PDO 是講好格式的廣播電台（即時）。面試必考。
💻 對照範例：learn/examples/l2/04-pdo-csp/（使能交握 + 斜坡跟隨全流程）；repo 實例 firmware/canopen/co_pdo.h/.c；co_pdo_feedback_seq() 的「序號判新舊」手法在 app_main.c 的 fb_fresh 安全判斷直接用上。

匯流排頻寬預算 — 為什麼是 500 Hz 不是 1 kHz

🎯 學會算 fieldbus 頻寬 — 系統架構師和抄範例的人，差別就在這一節。

一個 Classic CAN 8-byte frame 含 overhead + stuffing 約 130 bit → @1Mbps 一條 bus 每秒極限約 7000–8000 frame。套到單臂 7 軸：

控制頻率frame 數（7 軸 × RPDO+TPDO）結果
500 Hz7 × 2 × 500 = 7000 frame/s~90% 載荷，可行邊界 ✅
1 kHz7 × 2 × 1000 = 14000 frame/s超載 ~2 倍，必丟幀 ❌
firmware/app/control_rate.h — 把結論固化成程式碼
#define CONTROL_HZ    500.0f
#define CONTROL_DT    (1.0f / CONTROL_HZ)   /* 0.002 s */
#define CONTROL_DT_US 2000u                 /* TIM 週期(µs)，接回 L1-6 的 TIM6 */
  • 這就是本專案「雙臂拆兩條 bus（CAN1/CAN2）」的第一個理由：一條 bus 塞不下 14 軸
  • 第二個理由：故障隔離 — 一臂的線斷了不拖垮另一臂
  • 就算 500 Hz 也貼著上限跑，所以 dual_arm_tx_drops() 做了丟幀偵測
  • 要 1 kHz？換更快的匯流排 → 這就是 L3-17 EtherCAT 與專案 B 的入口
💻 對照範例：learn/examples/l2/05-bus-budget/（把這筆帳寫成計算器）；repo 實例 firmware/app/control_rate.h、firmware/README.md 頻寬警告、docs/design/can-bus-architecture.md、canopen-vs-ethercat.md。
130 bit/framebus load丟幀偵測雙 bus 架構

免硬體驗證 — 模擬器 · 單元測試 · SocketCAN

🎯 學會「沒板子也能開發」：同一份控制程式碼在 PC 上編譯、測試、跨行程對打。

本 repo 的控制邏輯全部寫成平台無關，HAL 依賴縮到最小，於是有三層驗證：

層怎麼跑repo 位置
單元測試cd firmware/tests && make — CiA402/PDO/IK/軌跡/安全逐一驗firmware/tests/test_*.c
HOST 模擬cmake -S firmware -B build && ./build/phu_sim_demo — 假 HAL + 假 PHU 關節跑整個控制棧firmware/sim/（hal_shim.c、phu_sim.c）
SocketCAN 對打PC 主站 vs Python 假從站，走 Linux 虛擬 CANfirmware/pc/pc_master + sim_py/can_slave.py
Linux 虛擬 CAN — 免任何硬體練 CANopen
sudo ip link add dev vcan0 type vcan && sudo ip link set up vcan0
sudo ip link add dev vcan1 type vcan && sudo ip link set up vcan1  # vcan0=左臂 vcan1=右臂

candump vcan0           # 看 bus 上所有 frame（除錯神器）
cansend vcan0 000#0100  # 手動送 NMT start-all
心法：「控制邏輯」與「硬體層」之間切一刀乾淨的介面（本 repo 是 co_bxcan.h 那 4 個函式），上面全部可以在 PC 上測。這一刀切得好不好，決定你除錯是用 printf 燒板子兩小時、還是 gdb 五分鐘。
