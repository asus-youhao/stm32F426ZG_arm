⚡ 專案 B — Linux RT EtherCAT 1kHz 主站

把主站從 MCU 搬上 Linux PREEMPT_RT PC，用 SOEM / IgH 走 EtherCAT CoE，突破 Classic CAN 的頻寬天花板，達成 14 軸 @1kHz DC 同步控制。這是本 repo feature/linux-*-ethercat-master 系列分支的實戰內容。
PREEMPT_RTSOEM / IgHCoE + CiA402 DC 同步CSP @1kHz

🗺️系統架構

跟專案 A 是「同一套控制腦、換一條脊椎」：CiA402/CSP 邏輯不變，載體從雙路 CAN 換成一條 EtherCAT 菊鏈，同步從無到 DC 硬體級。

專案 A（CANopen）專案 B（EtherCAT）
主站硬體STM32F746（裸機）Linux PC + RT kernel
控制頻率500 Hz（頻寬上限）1 kHz+（頻寬剩餘極大）
同步品質無硬體同步，靠主站節拍DC 硬體同步 <1µs
佈線2× 雙絞線 + 終端電阻1× 網路線菊鏈
難點頻寬預算、雙 bus 排程RT 調校、ESM/ESI 除錯、廠商生態

🏁里程碑 M1 → M6

M1

主站機建置 — RT kernel + 主站庫

🎯 一台可重現建置的即時主站機，cyclictest 過關。
  • 裝 PREEMPT_RT kernel，uname -a 帶 -rt
  • 編譯 SOEM 與 IgH（本 repo 收錄於 third_party/，建置腳本 setup_master_host.sh）
  • cyclictest -m -p90 -i1000 跑 10 分鐘，max latency < 100µs 級
  • 專用網卡一張（主站要 raw socket 獨占）
M2

從站掃描 — 看見你的關節

🎯 slaveinfo 列出 14 站，讀懂 ESI/EEPROM 的 PDO 佈局。
  • SOEM slaveinfo enp2s0 / IgH ethercat slaves 列出全部從站
  • 對照 EYOU 提供的 ESI XML，確認 RxPDO/TxPDO 內容與 SM 配置
  • 把每站的 Vendor ID / Product Code 記進組態檔
M3

PREOP — CoE SDO 組態

🎯 用 CoE SDO 讀寫 OD：模式、限位、插補週期 — L2-9 原樣重演。
  • 讀 0x1000/0x6041；寫 0x6060=8（CSP）
  • 設插補週期物件（0x60C2）= 1ms，與 DC 週期一致
  • 只碰手冊寫明的物件（見實戰紀錄的 0x2100 教訓）
M4

SAFEOP → OP + DC 同步

🎯 全部從站進 OP，過程資料開始 1kHz 流動，DC 對時生效。
  • PDO 映射進 IOmap，SAFEOP 下 TPDO 讀得到 statusword/位置
  • ec_configdc() 啟用 DC，量測從站間對時誤差
  • 進 OP 後 working counter 穩定 — 卡 SAFEOP 就去讀 AL status code（實戰紀錄有除錯工具）
M5

單軸 CSP @1kHz

🎯 一顆關節在 1kHz 下使能並跟隨正弦軌跡。
  • 1ms 迴圈內完成：收 TPDO → cia402_enable_step() → 發 RPDO（L3-18 骨架）
  • counts 換算：EYOU 介面組態實測為馬達端 19-bit × 減速比 101 = 52953088 counts/輸出圈（與專案 A 的輸出端 524288 不同 — 先驗證再動）
  • 記錄 following error，確認無週期性尖峰（尖峰 = RT 或 DC 沒調好）
M6

14 軸整臂 + 抖動報告

🎯 雙臂 14 站同鏈 @1kHz，出一份抖動/延遲量測報告收尾。
  • 14 站全 OP，1kHz 下 working counter 零錯誤連續 1 小時
  • 移植專案 A 的 L2~L4 控制棧（joint/task-space 程式碼直接重用）
  • 量測並比較：cycle 抖動、DC 對時誤差、end-to-end 延遲 vs 專案 A

📓實戰紀錄 — 本 repo 真實踩過的坑

這條路線本 repo 真的走過（見 git log 與 EtherCAT 系列分支），教科書不會寫的部分在這裡：

事件經過帶走的教訓
卡 SAFEOP 從站不肯進 OP。自製診斷工具（wd_read、phu_state）讀 AL status / watchdog 逐項排查 ESM 除錯要靠讀暫存器講證據，不是重開機碰運氣；診斷工具要進 repo
0x2100 廠商物件 誤觸廠商自定義物件造成行為異常；後來在廠商參考主站（gallop_ws 的 pysoem 腳本 + ESI）比對出正確組態序列，「不碰 0x2100」坐實為根因 有原廠參考實作就先抄流量：跑一次官方工具、錄 packet、照著做
EtherCAT 寫入被鎖 第四輪驗證發現關節的 EtherCAT 寫入被內建控制器的「控制權」鎖死，外部主站無法取得寫入權 → 專案定案改走 CANopen（= 專案 A 成為主線） 技術選型輸給生態整合是常態：協定再好，廠商韌體不開權限就是不行。預研階段就要驗「寫得進去」而不只是「讀得出來」
這一段的價值：面試講「我做過 EtherCAT」人人會；講得出「AL status 怎麼讀、SAFEOP 卡住怎麼系統性排查、廠商物件與控制權怎麼驗證」才是高階工程師的證據。失敗的分支也是作品集。

✅完成定義（Definition of Done）

  • M1–M4：可重現腳本建置 + 14 站進 OP + DC 同步量測數據
  • M5–M6：1kHz CSP 跟隨 + 抖動/延遲報告（與專案 A 的 500Hz 對照表）
  • 所有診斷工具與組態檔進 repo，換一台機器照 README 能重來
  • 若被廠商權限擋住（如本 repo 的遭遇）：把驗證證據寫成設計文件，選型結論有數據支撐 — 這也算完成
